# D阶段：Offer池、比较、材料交接与结束求职

> 状态：产品定义已确认，D阶段讨论完成。更新：2026-09-13。
> 本文替代原旅程J17—J22及此前D阶段方向记录。完成的是产品定义，不表示功能已经实现。

## 1. 阶段范围与工作

收到录用意向或正式Offer的岗位进入Offer池，用户维护录用条件、选择比较对象并办理交接。不同岗位独立推进：一个岗位进入Offer池时，其他岗位仍可以处于筛选、面试或准备中。

| 工作 | 用户要完成的工作 | 产品应保存的结果与规则 | Agent可以承担的工作 |
|---|---|---|---|
| J17 维护Offer | 查看意向或Offer，补充与HR确认的条件 | 保存关联岗位、录用情况与各项条件，区分意向和正式Offer；未知内容不补猜 | 整理已提供的录用信息，按需辅助维护，保留依据 |
| J18 比较Offer | 选择多个Offer并比较，按个人考虑作决定 | 保存对比对象、字段、信息来源和分析结果；个人条件与公开参考分开 | 查找所选公司的官方信息，结合用户条件解释差异与取舍 |
| J19、J20 材料交接 | 按实际要求准备、提交和核对材料，办理入职交接 | 每个Offer维护交接清单，关联原岗位；提交材料与办理完成分别表达 | 从通知整理事项，辅助准备，核对要求及完成情况 |
| J21 实习转正 | 收到转正考核时准备和参加，收到转正Offer后维护及比较 | 复用C阶段考核和D阶段Offer流程，不建设独立实习管理模块 | 沿用考核进程、准备、复盘与Offer能力 |
| J22 结束本轮求职 | 主动停止本轮求职，保留已有积累 | 停止本轮主动跟踪和提醒，保留资料及历史；根据用户确认情况呈现恭喜或祝福动画 | 响应结束操作，停止主动求职任务，不推测用户去向 |

J22是全局操作，用户在任何阶段都可使用，不要求先取得或接受Offer。

## 2. Offer池与可维护信息

### 页面与岗位关系

提供独立Offer池界面，集中展示已收到意向或正式Offer的岗位。用户可以查看、维护单个Offer，选择多个Offer进入对比，并查看具体Offer的材料交接事项。

Offer记录关联原岗位，继续使用已有公司信息、JD、岗位材料与进程。进入Offer池不创建一份脱离原岗位的重复档案，也不将其他岗位自动结束。

意向与正式Offer始终分别标识；收到意向不代表已取得正式录用承诺，收到Offer不代表用户已经接受，接受Offer不代表已经入职。

### 信息与比较维度

用户按需填写，允许部分信息为空，不以填满字段作为查看或比较的前提。

| 维度 | 可维护字段 | 主要依据 |
|---|---|---|
| 录用情况 | 意向或正式Offer、回复截止时间、附带条件 | 用户与HR沟通、录用通知或文件 |
| 工作内容 | 岗位、团队、实际职责、业务或产品 | JD、面试沟通；公司官网补充背景 |
| 地点与安排 | 实际办公地点、到岗时间、工作方式 | 用户与HR确认 |
| 薪酬 | 固定工资、发薪月数、浮动奖金、补贴、签字费、股权等适用项目 | 个人录用文件及用户确认的具体条件 |
| 福利与工作安排 | 社保公积金、假期、工时或排班等已确认内容 | 具体约定；官方政策作为补充参考 |
| 成长与发展 | 培训、导师、工作内容的学习空间、发展方向 | 官方信息、面试沟通及个人判断 |
| 个人考虑 | 喜欢的地方、顾虑、自定义比较项 | 用户自己填写 |

薪酬保留各组成项，不只保存一个总包数字。固定部分与浮动、附条件部分分别展示；涉及合计时说明计入项目和假设，不能把奖金或股权都当成保证现金收入。

### 信息来源与确认程度

| 信息类型 | 使用规则 |
|---|---|
| 个人录用条件 | 以用户与HR确认或提供的录用材料为依据；具体金额、到岗日期等不能从网上替用户确定 |
| 官方公开信息 | 用于补充公司业务、公开福利或培养体系等背景，保留链接和读取时间；公司层面的公开介绍不自动变成个人合同条件 |
| 他人公开经验 | 标明来源、时间与适用团队或范围，作为参考；不将个案推广为当前岗位的确定事实 |
| 个人判断 | 保留为用户的偏好、顾虑或评价，与外部事实区分 |
| 未知或未确认 | 直接显示缺失或未确认，不用其他公司的条件、他人待遇或模型猜测填补 |

Agent发现缺项时可指出需要确认的内容；用户自行选择是否补充。来源不一致时保留差异，不静默覆盖用户已确认的信息。

## 3. Offer比较

### 使用流程

1. 用户在Offer池选择要比较的多个岗位。
2. 产品按上述维度并排展示已有条件，明确意向、正式Offer及各项信息的确认程度。
3. Agent根据用户需要检索所选公司的官方信息，补充公开参考；使用他人经验时单独标识。
4. Agent解释实际差异、缺失信息和不同偏好下的取舍，用户决定选择哪个Offer或继续了解。

对比以并排事实为主体，不强制设置权重或生成一个总分冠军。用户可以围绕某个维度查看分析，例如更看重工作内容、固定收入或实际地点。

比较结果保留所用条件与来源。用户更新Offer信息后，已有分析不应继续被呈现为基于最新条件的结论；再次分析以更新后的信息为准。

### Agent分析边界

Agent能查到的是公开公司背景与参考信息，不能替代用户和HR确认私有条件。例如，A的固定工资已明确、B的奖金仍未确认时，应呈现这个差异，而不是直接用未经确认的B总包作高低排序。

招聘方未明确的团队氛围、工时、发展或收益不能由Agent保证。用户作最终选择；仅获得一个评分或推荐结果不会自动接受Offer。

### 比较任务与岗位隔离

普通岗位工作继续沿用B、C阶段的上下文隔离规则。用户主动选择多个Offer比较时，Agent才加载这些选中Offer的比较资料及相关个人偏好，不加载未选岗位，也不默认读取所选岗位全部面试对话。

对比结果作为比较任务的成果保存，不自动成为每个岗位工作台的上下文。回到某个岗位办理交接时，仍只使用该岗位资料和相关个人资料。

## 4. 材料交接

合并J19、J20。每个Offer维护一份交接清单，实际事项来自企业通知、办理页面及用户与招聘方的沟通，不预设所有人都必须完成相同流程。

| 清单信息 | 保存内容 |
|---|---|
| 事项 | 需要提交的材料或办理的交接工作 |
| 接收方与入口 | 交给谁、在哪个页面或渠道办理 |
| 时间 | 通知要求的提交或办理期限 |
| 办理情况 | 未完成、已提交、对方已确认完成等实际情况 |
| 依据与结果 | 原始要求、用户确认或收到的结果 |

Agent可以从邮件与实际页面整理清单，辅助准备和检查缺项；用户补充线下或其他渠道办理的结果。不能因为文件上传成功就把对方审核标成通过。

交接继续关联原岗位的工作台与进程，需要时间安排的事项沿用已有日程能力。产品不借此重新引入学校事务管理或个人生活安排。

## 5. 实习结束与转正

当前不建设独立的实习过程或转正管理系统。

| 实际情况 | 复用方式 |
|---|---|
| 收到转正考核通知 | 使用C阶段的进程、日程、针对性准备与复盘能力，保留这次考核的实际安排 |
| 收到转正意向或Offer | 进入Offer池，维护并比较对应条件，与原实习录用条件分开记录 |
| 实习结束但没有明确转正通知 | 不推断转正通过或失败；用户可继续已有求职流程或结束本轮求职 |

转正是已有能力适用的一个场景，不增加日常实习任务、绩效考核或工作管理模块。

## 6. 结束本轮求职

提供全局“结束本轮求职”开关。该操作由用户主动发起，不因收到Offer、接受Offer或某段时间没有活动而自动触发。

### 开关效果

- 停止本轮求职的主动邮件跟踪、自动推进任务和主动提醒。
- 保留个人资料、岗位材料、练习与复盘、Offer信息及历史记录，用户仍可查阅。
- 不改写外部招聘事实，不将其他岗位自动标记为被拒、撤回或已完成，也不向招聘方自动发送消息。
- 接受Offer与结束求职是两个独立操作；用户可以接受Offer后继续处理交接，再选择何时结束本轮使用。

开关作用于该用户本轮求职的主动任务，不停止B阶段由后端维护的公共公司招聘目录更新。

### 结束动画

| 用户确认的情况 | 动画语义 | 文案示例 |
|---|---|---|
| 已确定Offer，结束求职 | 恭喜用户开启新的旅程 | “恭喜你，开启新的旅程。” |
| 未确定Offer，暂时结束 | 通用祝福，不暗示失败 | “愿接下来的日子，顺遂自在。” |

动画在用户执行结束操作时呈现。未确定Offer不等于没有好的去向，不使用“别灰心”“继续加油”等带有鼓励或安慰预设的表达。

## 7. 完整使用示例

用户收到A公司的正式Offer和B公司的录用意向，两者进入Offer池，其他岗位仍可继续面试。用户补充A的薪酬和到岗日期，B尚未明确的条件保持未确认。

用户选择A、B比较。Agent加载这两个Offer的比较资料，查找公司公开背景，并解释已知差异与信息缺口。用户确认选择A后，按A的通知办理材料交接；办理时不带入B的专属资料。

用户决定停止本轮求职，使用总开关，产品停止主动跟踪和提醒、保留全部积累，并呈现恭喜动画。若用户没有确定Offer而选择结束，则呈现通用祝福动画。
