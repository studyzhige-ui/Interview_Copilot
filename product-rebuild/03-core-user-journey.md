# Interview Copilot 核心用户旅程

> 状态：已确认  
> 日期：2026-09-01  
> 上位文档：[01-product-definition.md](./01-product-definition.md)、[02-mvp-definition.md](./02-mvp-definition.md)  
> 本文描述用户如何完成 MVP 闭环。详细页面、字段、交互和技术实现由后续文档定义。

## 1. 旅程起点与终点

起点：用户开始寻找计算机或 AI 相关岗位，希望用一个持续工作的产品管理个人档案、多个机会、关键提醒、面试准备和复盘。

终点：用户管理着多个真实机会，完成了一次针对具体岗位的准备与复盘，并在下一次准备中看见此前经验产生的、可追溯且保持更新的影响。

## 2. 核心旅程

### 第一步：建立并维护个人档案

个人档案是用户自己维护的高权威事实源，至少覆盖：

- 个人信息；
- 个人优势；
- 期望职位；
- 工作经历；
- 项目经历；
- 教育经历；
- 资格证书；
- 社团或组织经历；
- 志愿者经历；
- 专业技能。

用户以结构化填空为主维护这些内容，并可以保存多个简历附件，识别其版本、更新时间和用途。档案体验参考“左侧章节导航、中间档案维护与预览、右侧附件及辅助信息”的三栏组织；完整度提示和诊断只能辅助用户完善内容，不能替用户改写事实。具体视觉和交互稍后设计。

Agent 不主动维护或静默改写个人档案。它只在完成任务时按需读取相关部分；后续如果发现可信来源与档案冲突，可以附带依据提出更新建议，但必须由用户确认后才能改变档案。上传简历也不会自动覆盖用户维护的正式信息。

个人档案、简历附件和 Agent Memory 必须保持独立：个人档案是用户维护的正式事实；简历是针对特定用途组织和表达信息的文件；Memory 是 Agent 从长期经历中形成的、可以修订和失效的理解。后两者都不能反向静默覆盖个人档案。

结果：产品拥有一份全面、稳定、可由用户修正的个人基础情况，Agent 不需要每次重新询问，也不会把模型推断当成用户事实。

### 第二步：创建并跟踪机会

“机会”表示一个具体岗位，是后续投递和流程管理的对象。用户新增机会时，最低只需填写公司和岗位名称；来源链接或 JD、地点、截止时间、当前阶段和备注等信息可以按实际情况补充。机会默认进入跟踪，用户可以在创建时取消跟踪。

用户既可以在界面创建机会，也可以用自然语言让 Agent 创建；两种方式执行相同的产品能力、遵守相同规则并得到相同结果。

Agent 根据个人档案或当前对话搜索、筛选和整理岗位，是一项可按需调用的能力，不是创建机会的前置步骤，也不必成为独立固定流程。只有用户选择加入，或明确要求 Agent 创建后，搜索结果才成为机会。

结果：用户获得若干明确、可持续跟踪的具体岗位，而不是一组没有进入求职流程的搜索结果。

### 第三步：持续更新多个流程

用户可以选择一个机会，在界面中更新其真实进展；也可以用自然语言说明变化，让 Agent 完成相同更新。任务表达不完整时，Agent 应先利用当前对话、机会信息和已有来源尽力消除歧义，只有仍无法可靠判断时才询问用户。

主动 Career Loop 可以监控已授权的邮件等信息源。当外部事件可能改变机会状态时，Agent 先生成待确认更新，附上简短来源摘要和可跳转的原始信息；用户确认后，变化才正式进入机会流程。

每一次重要推进都应尽可能保留简短、可信且可跳转的来源。Agent 的分析本身不是流程事实。

结果：用户操作、自然语言操作和外部事件触发最终更新的是同一份机会状态，同时保留用户控制权和验证入口。

### 第四步：知道现在发生了什么

用户打开产品后，首先看到两类信息：

1. **已确认提醒**：已经成为正式事实且与时间相关的事项，例如明天笔试、后天下午面试；
2. **待确认事项**：Agent 从邮件等来源发现、但尚未得到用户确认的流程变化。

两者的流转关系是：

```text
外部事件
→ Agent 分析并生成待确认事项
→ 用户查看来源并确认
→ 更新对应机会
→ 需要提醒的已确认事实进入提醒列表
```

尚未确认的内容不能提前进入提醒列表。每条提醒都可以作为结构化引用加入 Agent 的当前任务；用户可以在此基础上补充自然语言目标，例如引用某场面试并要求准备专项练习或模拟面试。Agent 读取与该引用相关的上下文，准备所需信息并把用户带入对应工作。

结果：用户能区分“已经确定的事情”和“等待自己确认的变化”，并能从信息直接开始下一项工作。

### 第五步：准备和练习面试

面试体验由三个相互连接的部分组成：

1. **专项学习与练习**：围绕基础知识、项目细节和已经暴露的薄弱点进行准备；
2. **模拟面试**：尽量还原真实面试官的提问节奏、追问方式和压力；
3. **面试复盘**：从模拟或真实面试中形成下一次可使用的经验。

本步骤主要覆盖前两部分。系统结合具体 JD、个人档案、简历、面试阶段和既有复盘确定准备重点。项目经历可以关联 GitHub 仓库等来源，使未来的 Agent 能够在获得授权后理解真实代码和项目细节，而不是只依赖简历中的概述。

用户可以自己进入专项练习或模拟面试，也可以让 Agent 根据当前机会和提醒准备必要信息并启动对应流程；真正的练习仍由用户完成。

结果：准备围绕用户和这次真实机会展开，而不是生成通用题目清单。

### 第六步：记录并复盘面试

面试后，用户导入录音、转录、文字记录，或直接复盘一次模拟面试。系统需要尽可能准确地完成语音转写、说话人分离和问答结构还原，并始终保留原始来源。

Agent 基于可定位的对话证据分析知识回答、项目表达、沟通方式、面试节奏和其他表现，形成完整报告以及可能值得长期保留的记忆候选。用户可以回到来源核验，也可以修正不准确的转写和分析。

结果：复盘不只是一段总结，而是一份从原始面试到观察、建议和记忆候选均可追溯的分析。

### 第七步：让经验持续更新后续准备

复盘可能产生不同类型的长期理解，例如知识和能力水平、项目掌握程度、回答习惯、面试风格以及已经证明有效的表现。这些内容属于 Agent Memory 的候选，不因一次模型分析就永久成立。

Memory Runtime 需要结合来源、时间、置信度和适用范围处理新增证据。当用户在后续面试中已经改善某个问题，新证据必须能够修订、取代或降低旧认识的适用性，不能让数月前的结论一直代表现在的用户。

下一次准备时，Agent 只读取与当前任务相关的个人档案、机会信息和长期记忆，并说明历史经验为什么与本次准备有关。记忆的提取、更新、冲突、失效和删除将在 Agent Harness 设计中单独冻结。

结果：用户看得见产品越来越了解自己，同时这种理解能够随新证据变化，而不是积累成不可控制的旧标签。MVP 闭环至此成立。

## 3. 整条旅程中的共同规则

- 用户通过界面和 Agent 获得相同的业务能力，改变同一份产品状态；
- Agent 应先利用已有上下文尽力完成任务，不把可以自行消除的歧义直接抛给用户；
- Agent 的主动运行来自授权来源、时间或事件触发，不等于擅自改变正式事实；
- 个人档案和外部事件更新属于高权威内容，必须保留用户确认边界；
- 流程事实、提醒、待确认事项、分析建议和长期记忆必须清楚区分；
- 重要信息尽可能保留简短、可信并可跳转的来源入口；
- Agent 工作失败或被停止时，已经确认的状态不得丢失，用户可以稍后继续。
