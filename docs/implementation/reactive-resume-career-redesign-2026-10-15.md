# 求职模块重构：Reactive Resume 源码对照与移植设计

日期：2026-10-15。本报告保留分析时的设计结论；实现现已落地，实际范围与验证结果见 [重构交付记录](career-redesign-delivery-2026-10-15.md)。

本项目基准 HEAD：`0029187c674c78f891693da1ca7fd2654268d9e6`，分析对象包含当前工作区未提交修改，不能把结论当作该提交本身的行为。上游参考：`reactive-resume/reactive-resume`，package version `6.0.3`，固定提交 `19e0518eb5ea1b2c84d785bc5ea2b6d6c9d7b043`。已克隆并阅读实际源码，没有启动上游应用，因此上游交互判断基于实现，而非浏览器验收。

## 1. 推荐决策

采用 Reactive Resume 的求职工作台、独立简历文档、针对岗位复制、材料版本和编辑体验；保留本项目 FastAPI、身份系统、文件资产、面试记录和 Agent runtime。前端组件与纯逻辑分模块移植，服务端用 Python 接到现有业务对象，不引入第二套登录、数据库和 Agent。

核心用户流程应为：保存岗位 → 准备简历/材料 → 记录实际投递 → 安排面试 → 练习/复盘 → 跟进或比较 Offer。任何一步都能回到同一个岗位详情。页面不是数据库对象的逐项展示。

必须区分三件事：个人档案是经历来源，简历是面向读者的可编辑文档，投递记录是某次实际使用了哪份材料。岗位专用简历的修改不能自动覆盖个人档案，后续简历修改也不能改变历史投递版本。

这些是源码结论；未做本地 UI 全流程重现的部分不标成运行验收结果。

## 4. 目标产品结构

求职工作区使用四个直接入口：**岗位、简历与材料、日程、统计**。Offer 比较是从岗位或统计进入的专用视图；提醒偏好归设置。个人档案保留在资料区，但明确为“个人经历与求职偏好”。

岗位默认列表，提供看板切换。列表直接显示公司/岗位、阶段、地点、下一步及时间、最近更新；搜索和筛选在列表顶部。移动端默认列表，不压缩六列看板。已结束岗位可筛选查看，归档单独控制。

岗位详情桌面可用侧栏快速查看，并支持独立详情地址；窄屏全屏。默认先显示当前阶段和下一步，再分为概览、材料、面试、记录。操作使用“记录投递”“安排面试”“添加跟进”“编辑岗位”“结束申请”；内部事件枚举不成为主操作菜单。

材料页展示独立文档，支持新建、导入、复制到某岗位、重命名、版本、导出和归档。简历编辑器左侧内容，中央实际分页预览，右侧按需打开样式或 Copilot。先交付可靠的中文模板和导出，不把模板数量当作完成标准。

从岗位选择简历后，可以创建该岗位专用副本；选择材料仅表示准备使用。点击“记录投递”，填写日期/渠道并选择具体版本，才产生投递快照。没有材料信息的历史投递允许未知，不能自动把今天默认简历填进去。

日程合并显示真实面试、用户跟进、Offer 回复期限，但每项仍有明确数据归属；完成跟进不会自动完成一场面试。统计优先显示投递量、阶段转化和待处理事项，保留样本与时间范围；复杂分组和估值按需打开。

## 5. 后端目标与数据边界

| 对象 | 最终职责 | 处理决定 |
| --- | --- | --- |
| CareerProfile | 用户确认的经历、联系方式、方向和约束 | 保留，退出简历文档主身份；AI 提取继续以候选修改形式进入 |
| Artifact / ArtifactVersion | 一份简历/求职信/作品集说明与不可变正式版本 | 保留为唯一文档身份；结构化编辑内容与格式参数需要版本化存储 |
| 文档草稿 | 自动保存中的当前内容、编辑会话与冲突版本 | 新增明确草稿责任，不能每次击键都追加正式 ArtifactVersion；发布/投递时冻结正式版本 |
| ArtifactJobRelation | 某文档用于某岗位准备 | 保留，不能当作已经投递 |
| ArtifactSubmissionSnapshot | 确切材料版本的实际使用记录 | 保留，新增与本次投递事件的明确关联，解决多次投递的归属歧义 |
| JobOpportunity | 一次具体岗位申请 | 保留 ID 与外部身份；补普通编辑、联系人/备注等实际缺口，不复制 application 表 |
| ProcessEvent | 已发生的流程变化和可追踪更正 | 保留；普通笔记不强行伪装成 recruiter_contact 等招聘事实 |
| NextAction | 用户计划的跟进/任务及其提醒 | 保留；下一步摘要从此对象和面试推导，不再造重复任务系统 |
| InterviewRecord | 真实面试与复盘/录音的关联身份 | 保留；不能像上游那样把面试完全放进 application.activity JSON |
| Offer | 条款、来源和回复期限 | 保留，入口收敛到岗位详情；比较用同一条款数据 |
| JobDescriptionSnapshot | 有来源、时间和版本的岗位描述 | 保留，支持无 URL 的粘贴来源，后续编辑创建新版本 |

阶段建议面向用户为：待投递、已投递、筛选/测评、面试、Offer、已结束。迁移不能按中文 `current_step` 猜阶段，而应重放有效的 typed events。旧 `in_process` 中无法确定细分的项保留“进行中/待细分”，不伪造面试记录。

后端应明确“当前阶段”与“历史到达阶段”：前者支持真实业务回退/重开，后者供漏斗使用。不能继续用最高阶段算法来解释全部看板操作。新增状态转换命令记录变更原因、版本、幂等键，和既有事件入口共用一个 reducer。重开后不自动复活因终态关闭的历史任务；新计划由用户明确创建。

建议在现有 career-process API 下增补业务能力，不再套一层平行业务服务：

- 岗位列表：服务端 q/stage/outcome/archive 筛选、稳定排序、分页与总数；单岗位 GET 独立于列表，解决深链接超出当前页的问题。
- 岗位普通编辑：expected_version + PATCH，可改公司、岗位、地点、链接、备注等，归属和 URL 规范化检查复用现有代码。
- 记录投递：同一事务写 ProcessEvent、渠道、精确材料快照、关联；operation_key 保证重试不重复。
- 详情读取：按岗位批量聚合行动、材料、面试、JD 和 Offer，避免前端下载用户所有对象再过滤；各子列表可分页。
- 面试安排：继续走共享 invitation operation，前端按“已有岗位”预填；不能建立第二条手工直写 InterviewRecord 的路径。
- 日历：只读投影；导出 ICS 不改变面试状态。
- CSV：解析与映射预览 → 校验错误和重复项 → 用户执行导入；不把每次重新导入当作新投递。

## 6. 保留、移除、延后清单

**必须保留：** 用户隔离、幂等、并发冲突控制；确切文档版本；JD 原文及时间；面试录音/练习/复盘关联；通知时区与安静时段；邀请确认；历史更正；可撤销合并；事实与 AI 建议的区分。这些承担数据责任，不因 UI 复杂而删除。

**应替换/收敛：** `CareerProcessPage` 的永久左右分栏大页面；`CareerInsightsPage` 把行动/统计/Offer/设置捆成一个页的结构；个人档案冒充文档编辑器；每个页面重复的缓存刷新代码；手工记录来源的内部字段；求职区重复的 Copilot 按钮；默认展开的长流水。对应能力迁完后删除旧实现，旧地址用重定向承接，不维持两套编辑器。

**后端只按职责拆分：** `process.py` 机会/事件/合并/行动职责可以分开，但共享归属检查和事务边界。拆文件本身不是简化；禁止新增通用 WorkflowManager、万能实体表或全新 Repository 层只为包装现有函数。

**不能立刻删除：** `models/resume.py` 的退役历史表和 `/resumes` 兼容地址。前者承载历史/迁移数据，后者当前上传、默认简历及面试调用仍在使用；完成引用迁移后再单独退役，不恢复其生产写入。

**不随本轮搬入：** 上游第二套账号/OAuth、公开简历站点与访问统计、第二套 AI/密钥管理、MCP 服务、赞助/营销、全部字体和模板、自定义 CSS 完整语言、所有外部岗位搜索供应商。它们不构成求职记录闭环的必要依赖。

**保留但降低优先级：** Offer 税后/股权估值的复杂输入、精细漏斗分组、批量操作、ATS 分数。上游 ATS/关键词规则属于启发式检查，不能包装为招聘系统通过率或能力评分。当前谈判草稿 `build_negotiation_draft` 是固定模板拼接，也不能当作已实现的动态 Agent 谈判。

## 7. 移植顺序与退出条件

1. **基线与检查点。** 保存当前 dirty checkout 的可恢复快照、数据库备份及本轮变更清单；隔离测试账户。锁定上游 SHA 和许可证。不把其他正在进行的修改 reset 掉。
2. **岗位纵向闭环。** 完成分页/编辑/阶段命令/详情聚合/投递事务，再接列表、详情和看板；保留全部旧记录及 ID。退出条件：新建、编辑、搜索第 101 条、记录投递、安排面试、结束/重开均可实际使用。
3. **文档闭环。** 分离档案和文档；引入简历 schema、草稿、版本、模板、预览和导出；从岗位复制和选择具体投递版本。退出条件：刷新恢复草稿、冲突不丢失、中文 PDF 可复制、分页无裁切、历史投递不漂移。
4. **日程与 Offer。** 聚合真实面试和行动，加入 ICS，迁移 Offer 入口及提醒设置；通知仍复用原服务。退出条件：改期/时区/终态关闭/截止提醒一致。
5. **统计和导入导出。** 以全量、明确投递事实计算，不以看板当前页计数；CSV 有预览与错误定位。退出条件：多次投递/多份材料不导致分母误计，导出可往返。
6. **正式切换与删除旧 UI。** 更新导航、Agent 工具深链接、活动引用和旧路由；核对公开 API 使用后再退役。完成回滚演练后清除临时代码。不能把只完成新版页面外观称为全量移植。

本计划的顺序是依赖关系，不是时间估算。PDF 依赖适配、历史数据迁移和真实 UI 验收尚未做，无法据此承诺整套代码可直接复制运行。

## 8. 数据迁移规则

- 保留 JobOpportunity/Artifact/InterviewRecord 主键，不做全量导出重建。
- 增量 migration 增加必要字段；先回填并校验，再切读写。新旧字段只在有明确退出条件的迁移窗口共存。
- 当前档案可以生成一份明确标识来源的初始简历；不能声称它是过去上传或投递的同一文件。
- 历史上传文件继续作为原始文件文档可打开；解析不完整时提示需要核对，不能用空 schema 覆盖原文。
- 历史投递只关联已有确切快照；缺失事件与版本关系标记 unknown，不用当前默认简历补历史。
- 当前终态造成的 archived_at 与用户主动归档无法仅凭同一字段区分，需要保守迁移并记录规则。
- 合并后的旧 ID 能解析到 canonical，同时保存来源关系；撤销合并后数据仍可还原。统计必须明确合并口径。
- 迁移检查至少覆盖各用户数量、文件 hash、版本数量、外键、时间/时区、终态和未完成任务。数据库恢复与代码回退必须配套。
