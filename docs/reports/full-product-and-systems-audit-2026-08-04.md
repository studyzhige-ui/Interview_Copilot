# Interview Copilot 全产品与核心系统审查（2026-08-04）

## 1. 结论先行

这次审查后的项目已经不再是“功能都能点，但边界和运行方式不清楚”的原型。
它现在有一套可解释的产品边界、一条共享代码主线、两个发行策略，以及能支撑
Community 发行候选版的核心架构。

项目当前应这样定位：

- **Community**：已经接近可发布的自部署 Release Candidate。核心业务、安装
  路径、数据基础设施和自动化测试具备闭环；发行前仍应在一台真正全新的机器上
  做一次安装与完整业务验收。
- **Cloud**：已经具备正确的产品代码边界，但还不是可直接宣称“商业生产就绪”
  的在线服务。监控、告警、配额、账单、备份恢复、隐私流程、容量与成本数据属于
  运营基础设施，不能只靠仓库代码假装完成。

这不是两套源码。Cloud 与 Community 共享领域模型、API、前端和任务链路，
`APP_EDITION` 只决定终端用户能配置什么，避免以后维护两份逐渐分叉的产品。

## 2. 产品边界

Interview Copilot 的核心目标是帮助候选人进行面试训练和复盘，不是招聘管理
系统、在线考试监考系统，也不承诺求职结果。完整用户闭环是：

1. 管理个人简历；
2. 添加可复用的技术、项目和面试资料；
3. 使用简历与岗位 JD 开始模拟面试；
4. 上传真实面试录音进行转录和复盘；
5. 在 Chat/Agent 中针对证据继续追问；
6. 从长期记忆和能力趋势中观察成长。

不同材料有明确归属：

| 数据 | 归属与用途 | 不应发生的行为 |
|---|---|---|
| 个人简历 | 独立 Resume 实体，最多两份，可选默认项 | 不自动混入通用知识库 |
| 模拟面试 JD | 本次面试的临时上下文和冻结快照 | 不因为一次使用永久污染资料库 |
| 知识文档 | 可复用 RAG 来源：题库、技术资料、项目资料 | 不伪装成个人简历 |
| 录音/转录/问答 | 归属一条面试记录 | 不脱离记录成为无主文件 |
| 长期记忆 | 从有证据的对话和复盘中提取 | 不把模型猜测直接当用户事实 |

模拟面试当前让用户选择真正影响体验的内容：简历、JD、面试官风格和音色。
阶段计划、追问预算、评分规则、内部模型和检索策略是产品质量策略，不暴露为一堆
“高级设置”。这样既减少错误配置，也让不同场次的结果仍具有可比较性。

Cloud 用户可选择最终回答模型、个人模型 Key、音色、个人 Skill 和远程 MCP。
内部规划/Worker 模型、Embedding、Reranker、解析、ASR、说话人分离、存储和
队列由平台负责。Community 部署者可替换所有实现，并可在可信环境中显式开启
stdio MCP 或自定义模型端点。

## 3. 审查范围与方法

本轮不是按文件数量做机械重写，而是沿真实业务链路审查：

- 上传、确认、解析、分块、Embedding、Milvus、混合召回、重排、水合与引用；
- Chat/Agent 的创建、用量观测、工具快照、MCP 生命周期、取消、重连和持久化；
- 模拟面试的准备、阶段推进、并发回答、结束、后台复盘和失败恢复；
- 真实录音分析、记忆提取、能力状态和雷达图证据；
- 模型选择、平台内部模型、Skill/MCP 的用户/会话/Turn 隔离；
- PostgreSQL、Redis、对象存储、Milvus、Outbox、Celery 队列和 Worker；
- API 的领域分组、同步/异步边界、前端信息架构和响应式布局；
- 迁移、Compose、脚本、单元/API/服务/架构测试及前端构建。

审查原则是：只有职责不同、资源模型不同或故障域不同，才增加边界。没有为了
“看起来像大厂”而拆微服务，也没有把同步 SQLAlchemy 全部改成异步这一类高成本、
低收益的重写。

## 4. 系统全景

```text
React
  -> FastAPI（鉴权、校验、短事务、SSE）
      -> PostgreSQL：业务事实和任务状态
      -> Redis：缓存、限流、Celery 运输
      -> S3/MinIO：原始文件与音频
      -> Milvus：可重建的检索索引
      -> LLM/语音/检索模型提供方

长任务
  -> 先持久化 record / turn / outbox
  -> 再投递 Celery
  -> 按 turns / pipeline / transcription / background / default 隔离
  -> Worker 幂等处理并写回持久状态
  -> 前端轮询或从可重连 SSE 继续读取
```

PostgreSQL 是生命周期的事实来源，Redis 不是；Milvus 是可重建索引，不能反过来
决定文档是否存在；对象存储拥有字节，但引用和消费状态仍在数据库中。

当前数据库是 26 张业务表、359 个字段。数量本身不是问题：账户、模型凭据、
会话、消息、Turn、工具调用、面试、问答、文件、知识、简历、记忆、能力和 Outbox
都有不同生命周期。审查没有发现把同一种 CRUD 无意义拆成多张表的充分证据。

## 6. 本轮发现并修复的高优先级问题

### 6.1 RAG 与上传链路

- API 启动曾提前加载 Embedding/Reranker，导致即使只访问账户接口也承担模型
  初始化成本。现在改为进程内加锁的惰性运行时，只在查询或对应 Worker 真正需要
  时加载。
- 文档摄取的业务状态曾与 Celery `autoretry_for` 不一致：不可重试异常仍会显示
  “将重试”，留下永久 processing。现在重试异常集合只有一个事实来源，终止异常
  明确写入 failed。
- 简历上传后，前端曾能在解析完成前启动面试，后端又可能静默使用空简历。现在
  前后端同时实施就绪门禁；解析中返回 409，解析失败提示替换，不再降级成空上下文。
- 简历列表曾存在 `/uploads/resumes` 与 `/resumes` 两套概念和返回结构。现在只保留
  Resume 领域 API，并补齐上传、替换、设为默认和删除的真实页面。
- 知识库的“简历”分类与个人简历实体重复。现在资料页明确分成知识库、简历、
  记忆；知识分类改为面试题库、技术资料、项目资料。

### 6.2 Agent 链路

- Step、工具调用数、Token 和耗时只作为可观测数据，不再用于截断任务。Agent
  根据模型最终回答、显式取消或上下文耗尽结束；单次请求/工具超时、上下文压缩和
  Worker 生命周期承担基础设施保护，避免把任意数字误当成任务完成条件。
- SDK 内部重试与应用级重试曾可能叠加，放大延迟和成本。现在 LLM SDK
  `max_retries=0`，统一由应用层决定是否重试，并设置请求超时。
- MCP 运行时取消时只取消当前调用，队列中等待的 Future 可能泄漏。现在取消会
  同时结束正在执行和未开始的调用。
- 用户 Skill/MCP 不修改全局工具注册表。工具集合从用户启停、Edition、部署能力、
  会话权限解析后，在 Turn 开始时冻结；Tool Call 再拥有参数、超时、Abort、审计
  和结果。这符合用户级到调用级逐层收窄，而不是“每 Turn 新建所有连接”。

### 6.3 模拟面试

- 原阶段只给了宽泛的最大问题数，模型可能过早跳阶段或无限深挖。现在业务层拥有
  最小/最大问题预算：自我介绍 1/1、项目 2/4、技术 3/6、候选人提问 1/2；模型
  不能向后跳、跨阶段跳或在非最终阶段结束。
- 全局安全上限从 30 个回答收敛到 14，既覆盖阶段上限，又避免异常会话持续消费。
- 同一个问题被双击或两个标签页同时回答，过去可能触发两次 LLM。现在数据库中有
  原子 Answer Claim、领取时间和过期回收；失败或取消会释放 Claim。
- 模拟复盘的模型任务从默认短任务队列移到 background，避免阻塞清理和调度。

### 6.4 能力与记忆

- 雷达图刷新过去会再次调用 LLM，既慢又会让同一份证据得到漂移分数。现在从
  `memory_ability_states` 确定性映射，展示证据数量和覆盖度。
- 缺失能力轴过去容易显示为 0，用户会误以为自己能力很差。现在缺失是“待评估”
  的 `null`，0 分只可能来自真实评分。
- 模型支持的记忆提取与文档索引曾共用 pipeline Outbox，慢 LLM 能造成队头阻塞。
  现在 Outbox 按 `job_type` 领取，并拆成 index、intelligence、cleanup 三个 drain。

### 6.5 API、数据库与执行模型

- 当前共有 94 条 `/api` 路由，按 auth、models、capabilities、chat、mock、records、
  resumes、knowledge、memory、analytics 等领域分组。数量来自资源生命周期，不是
  94 个服务；没有理由为追求“接口少”把不相同操作塞进万能接口。
- 使用同步 SQLAlchemy 的路由中，阻塞数据库/对象存储调用已改为普通 `def`，由
  FastAPI 线程池承载；真正 SSE/异步 I/O 才使用 `async def`。这比半异步、在事件
  循环里执行同步 SQL 更正确，也比全量改 AsyncSession 更简洁。
- Outbox 新增 `(job_type, status, next_run_at)` 领取索引；模拟面试运行态新增
  `(user_id, status, last_activity_at)` 索引，服务于真实扫描路径。
- 迁移在清空开发数据库后被压缩为一份当前基线，再以小型后续迁移承载本轮字段和
  索引。此策略适合尚未正式发行的 Community；一旦公开版本有用户数据，基线就应
  冻结，后续只能追加迁移。

### 6.6 前端信息架构

- 侧边栏从平铺功能改为“面试工作台 / 资料 / 配置”，默认落点从复盘改为模拟面试。
- 个人中心不再同时出现在侧栏和 TopBar。
- 复盘原来的三栏固定宽度在小屏不可用，现在移动端以“记录 / 内容 / 对话”切换，
  桌面端保留三栏效率。
- 模型、资料、能力、Skill/MCP 和模拟准备页补齐响应式间距、换行和横向表格边界。
- 能力页、简历页和上传流程都以持久状态显示 processing/failed/ready，不使用只在
  当前页面内成立的乐观假状态。

### 6.7 存储、诊断接口与质量口径

- 迁移 `0004` 将全部生命周期时间从历史 naive UTC 统一为 PostgreSQL
  `timestamp with time zone`。应用统一使用 `UTCDateTime`/`utc_now()`；旧 naive
  值只在兼容边界被解释为 UTC，读出后始终是 aware UTC。迁移测试用一条真实
  `0003` 数据验证时间瞬间不偏移。
- 只有应用按字典/数组操作的运行结构使用 JSONB，例如 Turn 快照、工具参数、
  Outbox payload 和能力证据。大块版本化模型快照、转录段落和供应商 wire 配置仍
  保持不透明 Text；没有查询需求时不为追求类型名而拆解文档边界。
- `/rag/query` 已明确为 Community/开发诊断面；Cloud 返回 404，且在加载 RAG
  模型之前拒绝请求。正式 Chat RAG 链路不受影响。
- 能力分数使用显式 `evidence-v2` 连续标尺：模型可输出一位小数的 0–100 实证分，
  报告只汇总真实数值证据，未评估维度保持 unknown，不再把 weak/stable 等标签
  伪映射成 35/75 等固定值。API、报告和前端都携带版本与聚合语义。
- 模拟面试评测新增六条有状态轨迹，覆盖完整四阶段、重复追问、候选人反问与结束、
  跑题拉回、中英混合和客户端断线恢复；每个 Turn 同时检查阶段机、问题重复、语言、
  事实依据、安全和自然度。

## 7. RAG 质量结论

RAG 的工程链路是当前项目最成熟的部分之一：上传对象经过确认，Worker 解析和
分块，PostgreSQL 保存可审计 chunk，Milvus 同时承载向量/稀疏召回，结果经 RRF、
Reranker，再回到 PostgreSQL 水合和存活校验，最后才进入带来源编号的上下文。

历史 `Hit@3 / Recall@3 = 94.61%` 不能继续当成有效质量结论。旧实现只检查与
参考答案的宽松词面重合，中文长文本的 Token 化不正确，而且 Recall@3 在相关总数
固定为 1 时实际上就是二值 Hit@3；它没有验证命中的文档是否真的是金标来源。

本轮已改为：

- 使用可回溯到原文和当前 chunk 的原子 evidence groups；同一事实的多个等价 passage
  以 alternatives 表示，不再用“命中任意一个常见词”冒充相关；
- 同时报告候选覆盖、严格证据命中、来源命中、MRR@3、nDCG@3、Evidence-group
  Recall@3、Document Recall@3 与上下文纯度；
- 加入 48 条中英双语同领域困难负例，并以真实第二租户 canary 验证隔离；
- 显式多意图问题按意图分别检索与重排后交错合并，12 条端到端金标要求多个来源均被
  覆盖；无证据或限定实体不受证据支持时，在调用回答模型前确定性拒答。

2026-08-08 的独立数据审查将评测集收口为 25 份多格式官方资料、421 条检索样本
（373 条正例、48 条困难负例）和 36 条轨迹样本。所有正例都使用可回溯到当前
384/64 索引的原子证据组；12 条为显式多意图、多文档端到端问题。固定 GPU 链的
Candidate Hit@20 为 `0.9961`，无阈值 Hit@3 为 `0.9651`；但冻结证据门后的 held-out
Hit@3 `0.9186`、nDCG@3 `0.8522`、Evidence-group Recall@3 `0.8727` 和 Query
Precision `0.9258` 没有全部达到发布门禁。因此本轮诚实标记为 `release_ready=false`，
并按协议没有运行付费 RAGAS。完整指标、格式切片和下一步边界见
`evaluation/README.zh.md` 与
`docs/reports/rag-evaluation-2026-08-08.md`。

## 8. Worker、队列与故障模型

五个队列对应五类资源和故障域：

| 队列 | 任务 | 为什么必须隔离 |
|---|---|---|
| `turns` | Chat/Agent Turn | 长连接、可取消、需重连事件和用量审计 |
| `pipeline` | 解析、Embedding、索引同步 | 模型/GPU 内存与批处理压力 |
| `transcription` | ASR、说话人分离 | 最重的本地模型和最长音频任务 |
| `background` | 面试复盘、记忆智能任务 | 慢 LLM，不应阻塞索引或清理 |
| `default` | 调度、目录、扫描和清理 | 只接收短控制任务，保证系统能自愈 |

生产/完整容器模式一类队列一个 Worker 服务；宿主开发为了少开进程，仅将四个
非 Turn 队列合并到一个 solo Worker，但路由语义保持一致。Celery 开启 late ack、
worker lost reject、prefetch=1 和大于任务上限的 visibility timeout。业务状态门禁、
Claim 与 Outbox 负责承受至少一次投递。

仍必须通过真实演练确认的不是代码结构，而是环境参数：Worker 在模型加载中被强杀、
Redis 重启、Milvus 短时不可用、对象存储断网、长音频超时、重复投递，以及恢复后
是否达到唯一终态。

## 9. 没有采用的“看起来高级”方案

- 没有把每个领域拆成独立微服务。当前规模下会增加部署、鉴权、Tracing 和一致性
  成本，却不会提升用户价值。
- 没有把 MinIO 换成所谓“商业数据库”。MinIO 是 S3 兼容对象存储，不是 Milvus
  的替代品；Community 使用 MinIO、Cloud 使用云厂商 S3/OSS/COS 是正确分层。
- 没有让 Redis 成为任务业务状态。Broker 消息可能丢失或重复，状态必须落数据库。
- 没有让每个异步函数都变成协程或把模型调用放进 API 进程。协程适合等待 I/O，
  不能消除 CPU/GPU 阻塞。
- 没有继续增加模型、设置项和面试模板。当前主要瓶颈是质量证据和发行验收，不是
  功能数量。

## 10. 剩余工作与停止边界

### Community 发行前必须完成

1. 在全新 Windows 或 Linux 环境执行 setup、start、注册、登录、找回密码；
2. 上传 PDF/DOCX 简历和知识文档，确认解析、检索、引用、替换和删除；
3. 完成一场多轮模拟面试和一次录音复盘；
4. 在独立评测环境重新跑 RAG 指标；
5. 做至少一次 Redis/Worker 强杀和恢复演练；
6. 核对 `.env`、模型缓存与 `data/` 的磁盘增长和清理策略。

### Cloud 商业化前必须完成

在 Community 条目之上，再完成生产域名/TLS、托管数据库与对象存储、集中日志、
指标/Tracing/告警、用户与模型配额、成本归集、备份恢复演练、隐私政策、数据导出
和删除流程、内容安全、滥用防护、供应商故障降级、灰度与回滚。还需要用真实目标
并发量做容量和成本模型。没有这些证据时，Cloud 只能称为可部署架构，不能称为
商业生产完成。

### 已关闭的原“后续技术债”（2026-08-05）

原列出的 JSON、naive UTC、Cloud `/rag/query`、能力标尺版本和单 Turn 模拟评测
五项均已落实为代码、迁移和自动化测试，不再作为模糊的“以后再做”。对应边界见
6.7：不透明文档保留 Text 是有意的数据契约，不是遗漏；真实样本到来后新增评分
标尺版本是后续产品校准，不允许覆盖 `evidence-v2`。

仍需外部证据的事项没有被伪装成代码债：真人体验研究、故障与备份恢复演练、全新机器发行验收，以及 Cloud
的运营体系。这些工作需要真实模型、环境、用户或运营决策，仓库中的假数据不能
代替其结论。

## 12. 最终判断

项目优秀与否不再取决于继续加入多少 Agent 名词或基础设施，而取决于三件事：

1. 用户能否不理解内部架构也顺利完成“准备—练习—复盘—成长”；
2. 每个异步步骤是否有唯一、可恢复、可解释的状态；
3. 质量结论是否来自真实评测和运营数据，而不是模型自评或漂亮但无效的指标。

本轮已经把前两项的主要代码缺口收敛，并纠正了第三项的评测方法。下一阶段最有
价值的工作不是继续大改架构，而是在隔离环境完成发行验收、真实评测和故障演练，
再根据证据做小而准确的迭代。
